# Model Card: Price Predictor (прогноз цены закрытия)

Карточка составлена по шаблону Google Model Cards.

## 1. Сведения о модели (Model Details)

| | |
|---|---|
| **Название** | `Price_Predictor_{instrument_uid}_{interval}` (имя в MLflow Model Registry) |
| **Проект** | «Автоматизация ML-пайплайна для прогнозирования движения цен акций на основе исторических рыночных данных» |
| **Дата карточки** | 10.10.2026 |
| **Версия сервиса** | 0.1.0; версии моделей ведутся в MLflow Model Registry |
| **Тип модели** | AutoML-ансамбль моделей прогнозирования временных рядов |
| **Фреймворк** | AutoGluon TimeSeries 1.4.0 (`TimeSeriesPredictor`), PyTorch 2.2.2 (CPU) |

**Как устроена модель.** Отдельная модель обучается для каждой пары «инструмент + таймфрейм». AutoGluon с пресетом `medium_quality` обучает набор кандидатов и строит из них взвешенный ансамбль. Итоговый состав и качество каждого кандидата сохраняются в leaderboard.

Кандидаты, наблюдавшиеся в запусках проекта (MLflow, Grafana):

| Класс | Модели |
|---|---|
| Наивные базовые | `Naive`, `SeasonalNaive` |
| Статистические | `ETS`, `Theta` |
| Табличные (градиентный бустинг на лагах) | `RecursiveTabular`, `DirectTabular` |
| Нейросетевые | `TemporalFusionTransformer`, `Chronos[bolt_small]` (предобученная модель) |
| Ансамбль | `WeightedEnsemble` — взвешенная комбинация перечисленных моделей |

Состав зависит от лимита времени: модели, не успевшие обучиться, в ансамбль не попадают.

**Место в системе.** Модель — третий блок пайплайна: сбор данных (`data-ingestion-service`, T-Invest API) → расчёт признаков (`data-feature-engineering-service`, обмен через Kafka) → AutoML-обучение и инференс (`model-processing-service`) → валидация и мониторинг (MLflow, Prometheus, Grafana, Loki). Сервис поставляется Docker-образом (CPU-сборка PyTorch, около 920 МБ) и разворачивается через GitHub Actions.

**Параметры обучения** ([app/config.py](app/config.py), [app/ml_service.py](app/ml_service.py)):

| Параметр | Значение по умолчанию |
|---|---|
| Горизонт прогноза (`PREDICTION_LENGTH`) | 1 шаг |
| Целевая переменная (`TARGET`) | `close` |
| Метрика отбора (`eval_metric`) | MAPE |
| Пресет | `medium_quality` |
| Лимит времени обучения (`TRAINING_TIME_LIMIT`) | 120 с (через API — от 30 до 3600 с) |
| Минимум свечей для обучения / прогноза | 100 / 30 |

**Артефакты.** Каталог `models/{instrument_uid}__{interval}/` (предиктор AutoGluon, `meta.json`, `leaderboard.csv`); те же артефакты и pyfunc-обёртка — в MLflow (эксперимент `Price_Predictor_{instrument_uid}_{interval}`); запись об обучении — в таблице PostgreSQL `model_training_runs`.

## 2. Назначение (Intended Use)

**Бизнес-контекст.** Трейдеры, управляющие портфелями и частные инвесторы принимают решения о сделках в условиях неопределённости; ручной анализ истории котировок и индикаторов занимает много времени и подвержен когнитивным искажениям, а рыночные паттерны меняются, поэтому модель нужно регулярно обновлять. Проект автоматизирует этот цикл.

**Решаемая задача.** Регрессия на временном ряде: точечный и вероятностный прогноз цены закрытия следующей свечи биржевого инструмента по истории OHLCV-свечей.

**Основное применение.**
- учебно-исследовательский MLOps-проект: полный цикл «обучение → реестр моделей → инференс по запросу и по расписанию → мониторинг»;
- вспомогательный сигнал о направлении и величине ожидаемого изменения цены (`change_pct`) для аналитика.

**Целевые пользователи.** Разработчики и ML-инженеры проекта, аналитики, использующие прогноз как один из входов.

**Недопустимое применение (out of scope).**
- автоматическое исполнение сделок и управление реальными средствами без участия человека;
- использование как индивидуальной инвестиционной рекомендации;
- прогноз дальше одного шага, прогноз для инструментов и таймфреймов, на которых модель не обучалась;
- работа в периоды, когда нет завершённых свежих свечей (приостановка торгов, новый инструмент с короткой историей).

## 3. Входные и выходные данные

### Вход

Свечи из таблицы `candles` (PostgreSQL, заполняется соседним сервисом сбора рыночных данных), только завершённые (`is_complete = TRUE`):

| Поле | Тип | Описание |
|---|---|---|
| `time` | timestamp (UTC) | Время открытия свечи |
| `open`, `high`, `low`, `close` | float | Цены свечи |
| `volume` | float | Объём торгов |

Запрос к API: `instrument_uid`, `interval` (`1MIN`, `5MIN`, `15MIN`, `30MIN`, `1HOUR`, `2HOUR`, `4HOUR`, `1DAY`, `1WEEK`, `1MONTH`), для прогноза — `lookback` (30–500 свечей, по умолчанию 60; в задачах по расписанию — 100).

### Признаки

Из свечей рассчитываются 25 технических признаков (`add_technical_features`), которые передаются модели как ковариаты прошлого (past covariates):

| Группа | Признаки |
|---|---|
| Геометрия свечи | `body`, `body_pct`, `shadow_upper`, `shadow_lower`, `hl_spread` |
| Скользящие средние | `ma_5`, `ma_10`, `ma_20` и относительные отклонения `ma_*_dist` |
| Тренд | `ema_12`, `ema_26`, `macd`, `macd_signal` |
| Осцилляторы | `rsi` (период 14) |
| Волатильность | `bb_upper`, `bb_lower`, `bb_pct` (полосы Боллинджера, 20 свечей, 2σ) |
| Объём | `vol_ma20`, `vol_ratio` |
| Доходности | `ret_1d`, `ret_2d`, `ret_3d`, `ret_5d` |

Сырые `open`, `high`, `low`, `volume` в модель напрямую не подаются. Первые 19 строк после расчёта скользящих окон отбрасываются.

### Выход

Ответ `POST /api/v1/predict`:

| Поле | Описание |
|---|---|
| `predicted_close` | Прогноз цены закрытия следующей свечи (среднее предсказанного распределения) |
| `confidence_interval.lower_90` / `upper_90` | Квантили 0.1 и 0.9 прогноза |
| `last_close`, `last_candle_time` | Последняя известная цена закрытия и время её свечи |
| `change_pct` | Ожидаемое изменение относительно `last_close`, % |
| `prediction_date` | Дата, на которую дан прогноз |
| `model_used` | Имя лучшей модели из leaderboard |

## 4. Факторы (Factors)

Качество прогноза зависит от:
- **инструмента** — ликвидность, волатильность, корпоративные события (дивидендные гэпы, сплиты);
- **таймфрейма** — на внутридневных интервалах выше доля шума и есть ночные разрывы;
- **рыночного режима** — тренд, флэт, периоды резкой волатильности и новостных шоков;
- **объёма истории** — модель обучается на всей доступной истории инструмента, минимум 100 свечей;
- **календаря** — выходные и праздничные дни, пропуски в свечах.

Разбивка качества по этим факторам сейчас не выполняется (см. раздел 9).

## 5. Метрики (Metrics)

**Качество модели**

| Метрика | Где считается | Назначение |
|---|---|---|
| MAPE (`best_mape`) | валидационное окно AutoGluon | основная метрика, по ней отбираются модели и веса ансамбля |
| MAPE по каждому кандидату (`mape_{model}`) | leaderboard | сравнение моделей внутри запуска |
| Время обучения кандидата (`fit_time_{model}`) | leaderboard | стоимость обучения |

MAPE = среднее |y − ŷ| / |y|; в коде хранится в долях (0.01 = 1 %). Выбрана потому, что не зависит от масштаба цены и позволяет сравнивать инструменты между собой.

**Эксплуатационные метрики** (Prometheus → Grafana, [app/metrics.py](app/metrics.py)): `model_best_mape`, `model_leaderboard_mape`, `model_training_samples_total`, `model_training_duration_seconds`, `model_training_runs_total`, `model_prediction_total`, `model_prediction_duration_seconds`, `model_predicted_change_pct` (распределение прогнозируемых изменений — косвенный индикатор дрейфа), `model_predicted_close_price`, метрики планировщика `scheduler_job_*`.

**Пороговые значения на дашборде Grafana**

| Показатель | Норма | Внимание | Критично |
|---|---|---|---|
| MAPE лучшей модели | до 3 % | 3–7 % | более 7 % (вероятная деградация) |
| Доля ответов HTTP 5xx | менее 1 % | 1–5 % | более 5 % |
| Доля ошибок задач планировщика | менее 5 % | 5–20 % | более 20 % |

Для длительностей обучения, инференса и задач планировщика на дашборде строятся квантили P50/P95 (для HTTP — также P99).

Каждый прогноз по расписанию дополнительно логируется в MLflow (эксперимент `Inference_{instrument_uid}_{interval}`), вызовы `predict_next_close` трассируются через `mlflow.trace`.

## 6. Данные для оценки (Evaluation Data)

Отдельной отложенной (hold-out) выборки нет. Оценка — внутренняя валидация AutoGluon: последние `prediction_length` точек обучающего ряда. При горизонте 1 это **одна точка**, то есть `best_mape` — ошибка на одной свече.

## 7. Обучающие данные (Training Data)

- **Источник:** таблица `candles` — исторические свечи биржевых инструментов, которые `data-ingestion-service` получает из T-Invest API (API Т-Инвестиций) в историческом и потоковом режимах. Инструмент по умолчанию — `e6123145-9665-43e0-8413-cd61b8aa9b13` (акции Сбербанка), таймфрейм `1DAY`. В проекте модели обучались на минутных, часовых и дневных свечах этого инструмента.
- **Объём:** вся доступная история завершённых свечей по паре «инструмент + таймфрейм»; диапазон дат и число строк фиксируются в MLflow (теги `dataset_start`, `dataset_end`, параметр `training_samples`) и в `model_training_runs`.
- **Предобработка:** сортировка по времени, расчёт технических признаков, удаление строк с пропусками, приведение ряда к регулярной частоте таймфрейма средствами AutoGluon.
- Данные не содержат персональной информации.

## 8. Количественный анализ (Quantitative Analyses)

**Запуск из отчёта по проекту** — минутные свечи акций Сбербанка, 8 моделей в leaderboard (метрики запуска в MLflow):

| Модель | MAPE (доли) | MAPE, % |
|---|---|---|
| `WeightedEnsemble` (лучшая) | 8.9 · 10⁻⁹ | 0.0000009 |
| `SeasonalNaive` | 6.20 · 10⁻⁵ | 0.0062 |
| `RecursiveTabular` | 1.26 · 10⁻⁴ | 0.0126 |
| `Chronos[bolt_small]` | 2.12 · 10⁻⁴ | 0.0212 |
| `DirectTabular` | 2.25 · 10⁻⁴ | 0.0225 |
| `Theta` | 2.31 · 10⁻⁴ | 0.0231 |
| `Naive` | 2.48 · 10⁻⁴ | 0.0248 |
| `ETS` | 2.48 · 10⁻⁴ | 0.0248 |

**Как читать эти цифры.**
- Ошибка всех моделей, включая наивные, — сотые доли процента. Это свойство данных: цена за одну минуту почти не меняется, и прогноз «следующая цена равна текущей» уже даёт MAPE 0.025 %. Задача восстановления уровня цены на таком горизонте проста, и это не равно умению предсказывать направление движения.
- Одиночные модели отличаются от наивного прогноза не более чем в 2–4 раза, а `SeasonalNaive` обходит все обучаемые модели — преимущество сложных моделей не показано.
- MAPE ансамбля на четыре порядка ниже, чем у любой входящей в него модели. Вероятное объяснение — валидация на одной точке (раздел 6): веса ансамбля подбираются на той же точке, и комбинация прогнозов, лежащих по разные стороны от факта, попадает в неё почти точно. Это подгонка под валидацию, а не реальная точность; в отчёте по проекту также отмечено, что столь малые значения требуют дополнительной проверки на инерционность цены и утечку данных.

Результаты по другим таймфреймам (`1DAY`, `1HOUR`) в карточку не внесены. Актуальные значения доступны:

- `GET /api/v1/best` — последняя успешная модель и её MAPE по каждой паре;
- `GET /api/v1/runs/{run_id}/leaderboard` — качество всех кандидатов запуска;
- MLflow, эксперимент `Price_Predictor_{instrument_uid}_{interval}`;
- Grafana, панели «MAPE лучшей модели» и «Leaderboard — MAPE всех моделей».

## 9. Ограничения и особенности применения (Caveats and Recommendations)

**Ограничения постановки**
- Модель опирается только на историю цены и объёма одного инструмента. Новости, отчётность, макроданные, стакан заявок и связи между инструментами не учитываются.
- Транзакционные издержки, проскальзывание и ликвидность не моделируются.

**Ограничения оценки**
- Валидация на одной точке (раздел 6) даёт статистически ненадёжную оценку и позволяет ансамблю подогнаться под эту точку (раздел 8).
- Leaderboard строится на тех же данных, на которых шло обучение, и сортируется по ошибке на них; поэтому `best_model` / `model_used` может не совпадать с моделью, которой предиктор реально делает прогноз, а `best_mape` берётся из валидационной оценки этой строки.
- Фактическая ошибка прогнозов в эксплуатации (прогноз против реализовавшейся цены) не отслеживается.

**Особенности реализации**
- Загруженная модель кэшируется в памяти процесса и после переобучения не обновляется до перезапуска сервиса.
- Переобучение запускается только вручную (`POST /api/v1/`); автоматического переобучения и контроля дрейфа данных нет.
- При лимите обучения 120 с часть моделей пресета может не успеть обучиться, состав ансамбля меняется от запуска к запуску.

**Рекомендации**
- Использовать прогноз только как вспомогательный сигнал, решение оставлять за человеком.
- Перед использованием модели сравнивать MAPE одиночных моделей с `Naive` и `SeasonalNaive` в leaderboard того же запуска; оценке ансамбля не доверять, пока валидация идёт на одной точке.
- Переобучать модель регулярно и после резких изменений рынка; после переобучения перезапускать сервис.
- Для надёжной оценки добавить бэктест на нескольких окнах (`num_val_windows`), отложенную выборку и учёт фактической ошибки прогнозов.

## 10. Этические аспекты (Ethical Considerations)

- **Финансовый риск.** Решения на основе прогноза могут привести к убыткам. Модель не является инвестиционной рекомендацией, и её выводы не должны подаваться пользователям как таковая.
- **Избыточное доверие.** Интервал прогноза и низкий MAPE создают впечатление точности, не подтверждённое оценкой (раздел 9).
- **Данные.** Используются только обезличенные рыночные данные; персональные данные не обрабатываются. Условия использования T-Invest API могут ограничивать распространение исходных свечей и производных от них результатов.
